# פנקס המטבח — מפרט להעברה ל-Claude Code

מסמך זה מתאר אפליקציית ניהול קייטרינג קיימת (כרגע רצה כארטיפקט בתוך Claude.ai) שיש להפוך לאתר אינטרנט עצמאי עם מסד נתונים אמיתי, התחברות משתמשים וסנכרון בזמן אמת. המסמך כולל את כל המודל, הלוגיקה העסקית והמסכים כדי שתהיה אפשרות לשחזר את הכל במדויק בסביבה החדשה.

**קובץ מצורף:** `kitchen-ledger.html` — היישום העובד הנוכחי (HTML+JS בקובץ אחד, ללא מסגרת עבודה), לשימוש כהפניה ללוגיקה המדויקת בעת הצורך.

---

## 1. רקע ומטרת המוצר

כלי לניהול עסק קייטרינג פרטי: ניהול ספריית מרכיבים, ספקים, ציוד וסועדים; בניית מתכונים מודולריים (הכנות שמשמשות כרכיבים בתוך מנות אחרות); וניהול אירועים שמייצרים אוטומטית רשימת קניות, רשימת הכנות, ציוד לקחת ואומדן עלויות.

## 2. דרישות לא-פונקציונליות (הסיבה למעבר מהארטיפקט)

- **אתר אינטרנט מלא** + **PWA / אפליקציית מובייל** (מסך בית בטלפון) לגישה מהיר בשטח.
- **מסד נתונים אמיתי** (מומלץ: Postgres דרך Supabase — נותן גם DB, גם Auth, גם Realtime באריזה אחת. חלופה: Firebase).
- **התחברות משתמשים** (מייל+סיסמה או magic link) — כל עובד עם חשבון משלו.
- **הרשאות** (לשקול): "מנהל" (עריכה מלאה, כולל מחיקה/איפוס) מול "עובד" (יכול לצפות ולסמן צ'קבוקסים באירועים, אולי לא למחוק מתכונים/מרכיבים).
- **סנכרון בזמן אמת** — כשעובד מסמן הכנה כגמורה באירוע, זה מתעדכן מיידית אצל כולם (Supabase Realtime subscriptions / Firestore listeners).
- **קישור קבוע** שלא משתנה בכל עדכון (בניגוד להתנהגות הארטיפקט הנוכחית שיוצרת קישור חדש בכל פרסום).

## 3. מודל הנתונים

כל הישויות משותפות לכל הצוות (לא סקופ פר-משתמש), עם ID ייחודי (UUID) לכל רשומה.

### 3.1 Ingredient (מרכיב)
```
id: string (uuid)
name: string                    // שם המרכיב כפי שמופיע במתכונים (חובה)
unit: string                    // יחידת מידה לשימוש במתכון, למשל "גרם", "ק"ג", "יח'" (טקסט חופשי)
supplierId: string | null       // הפניה ל-Supplier
purchaseName: string            // אופציונלי. שם המוצר שנרכש בפועל אם שונה מ-name (למשל "קלחי תירס" לעומת "תירס גרעינים")
purchaseUnit: string            // אופציונלי. יחידת הרכישה אם שונה מ-unit
yieldPercent: number | null     // אופציונלי, 1-100. אחוז התפוקה מהמוצר הנרכש למרכיב הנקי במתכון
price: number | null            // מחיר ליחידת רכישה (₪, לפני מע"מ) — ראו סעיף 4.5 לגבי איך זה מחושב
```

**לוגיקת יחס רכישה/פחת (חשוב מאוד):**
אם `yieldPercent` מוגדר (בין 1 ל-99, לא כולל 100), אז עבור כמות נטו הדרושה למתכון (`netAmount`), הכמות לרכישה בפועל היא:
```
purchaseAmount = netAmount / (yieldPercent / 100)
```
אם `yieldPercent` ריק/0/100, `purchaseAmount = netAmount` (אין המרה).
השם והיחידה המוצגים ברשימת הקניות הם `purchaseName`/`purchaseUnit` אם הוגדרו, אחרת `name`/`unit`.
**מחיר תמיד מחושב כנגד `purchaseAmount`, לא `netAmount`** — כי המחיר הוא מה ששילמתם בפועל לספק על המוצר הנרכש.

### 3.2 Supplier (ספק)
```
id: string
name: string
note: string   // הערה חופשית, לדוגמה טלפון
```
רשימה סגורה — מרכיבים בוחרים ספק מתוכה (dropdown), לא טקסט חופשי.

### 3.3 Equipment (ציוד)
```
id: string
name: string
note: string
```
רשימה סגורה — גם היא, ציוד נבחר ממנה במתכונים.

### 3.4 Guest (סועד)
```
id: string
name: string
phone: string           // אופציונלי
restrictions: string    // הגבלות תזונה, טקסט חופשי, אופציונלי
```
רשימה סגורה, שמשמשת לשיבוץ בתוך אירועים (סועד יכול להופיע בכמה אירועים — לקוחות חוזרים).

### 3.5 Recipe (מתכון) — הישות המרכזית והמורכבת ביותר
```
id: string
name: string
type: 'dish' | 'prep'          // 'dish' = מנה סופית (מוצגת בתפריט אירוע), 'prep' = הכנה (רכיב פנימי בלבד)
baseAmount: number             // כמות בסיס, למשל 10 (מנות) או 1000 (גרם)
baseUnit: string                // יחידת הבסיס, טקסט חופשי: "מנות" / "גרם" / "ליטר" / "יח'" וכו'
components: Component[]         // ראו למטה
prepSteps: { id, text }[]       // שלבי הכנה, טקסט חופשי, מוצגים כרשימה ממוספרת
prepEquipment: EquipRef[]       // ציוד הנדרש בשלב ההכנה בבית (לא נלקח לאירוע)
eventEquipment: EquipRef[]      // ציוד שצריך לקחת לאירוע
```

**Component** (רכיב בתוך מתכון) — יש שני סוגים, מערך אחד מעורב:
```
// רכיב גלם:
{ kind: 'ingredient', ingredientId: string, amount: number }
// הכמות היא ביחידת ה-unit של אותו Ingredient, בהתאם לכמות הבסיס (baseAmount) של המתכון הזה עצמו

// מתכון בתוך מתכון (קינון, רקורסיבי — מנה יכולה להכיל הכנה, הכנה יכולה להכיל הכנה אחרת):
{ kind: 'recipe', recipeId: string, amount: number }
// הכמות היא ביחידת ה-baseUnit של המתכון-הבן, ביחס לכמות הבסיס של המתכון הנוכחי
```

**EquipRef:**
```
{ equipId: string, qty: number }   // qty ברירת מחדל 1, ניתן לשינוי (למשל "4 סירים")
```

**חשוב — מניעת מעגליות:** מתכון לא יכול להכיל את עצמו כרכיב, ישירות או דרך שרשרת (A מכיל B, B מכיל A). יש לאמת זאת גם ב-UI (לסנן את רשימת המתכונים הזמינים להוספה) וגם בשרת/ב-DB (constraint או ולידציה בזמן שמירה).

### 3.6 Event (אירוע)
```
id: string
name: string
date: string               // ISO date, אופציונלי
eventType: 'onsite' | 'offsite'   // 'onsite' = אצלנו (לא מציגים ציוד/פריטים לקחת), 'offsite' = אירוע חוץ
location: string           // כתובת (offsite) או הערה (onsite), אופציונלי
guests: number              // כמות סועדים כוללת
notes: string               // הערות חופשיות לאירוע, אופציונלי — מוצג בסיכום
menu: { recipeId: string, servings: number }[]   // רק מתכונים מסוג 'dish' יכולים להופיע כאן
guestSeats: (string | null)[]   // מערך באורך guests. כל תא: guestId או null (מושב לא משובץ)
```

**סנכרון guestSeats לאורך `guests`:** בכל שינוי של `guests`, יש להאריך/לקצר את המערך כך שאורכו תמיד שווה למספר הסועדים (padding עם null, או חיתוך מהסוף).

## 4. לוגיקה עסקית — אלגוריתמים לשחזור מדויק

זה הלב של האפליקציה. כל הפונקציות הבאות הן רקורסיביות ועובדות מעל עץ הרכיבים (dish → prep → prep → ingredient...).

### 4.1 שקלול כמויות (scale factor)
לכל רשומת תפריט באירוע `{recipeId, servings}`:
```
factor = servings / recipe.baseAmount
```
כאשר יורדים לרכיב-מתכון מקונן `{kind:'recipe', recipeId: childId, amount}` בתוך מתכון עם factor נתון:
```
childFactor = (amount * factor) / child.baseAmount
```
וממשיכים רקורסיבית עם ה-childFactor החדש.

### 4.2 אגרגציית רשימת קניות (aggregateIngredients)
מעבר רקורסיבי על עץ הרכיבים החל מכל מנה בתפריט האירוע, עם **cycle guard** (Set של recipeId שכבר בביקור בנתיב הנוכחי, למניעת לולאה אינסופית). לכל רכיב-גלם שנתקלים בו:
```
totalAmount[ingredientId] += component.amount * factor_at_that_point
```
התוצאה: Map של ingredientId → כמות נטו כוללת (מסוכמת מכל המופעים בכל המתכונים/אירועים, גם אם אותו מרכיב מופיע בכמה מנות).

לאחר מכן, לכל שורה בתוצאה: המרה לכמות רכישה לפי סעיף 3.1 (`purchaseAmountForIngredient`), וקיבוץ הרשימה **לפי ספק** (מרכיבים ללא ספק מקובצים תחת "ללא ספק מוגדר", בסוף הרשימה).

### 4.3 עץ הכנות מקונן (prep tree) — לא רשימה שטוחה!
דרישה חשובה: ברשימת ההכנות של אירוע, כל הכנה (prep) שמשמשת מנה מסוימת **מוצגת מקוננת מתחת לאותה מנה, מוזחת פנימה** (indentation לפי עומק). האלגוריתם:

1. חישוב Map גלובלי של `recipeId → {recipe, totalAmount}` (סכימה של הכמות הנדרשת מכל אותו מתכון על פני כל האירוע, גם אם משמש בכמה מנות — בדיוק כמו סעיף 4.2 אבל ברמת "כמה מהמתכון-הזה-עצמו נדרש", לא ברמת מרכיבי הגלם).
2. רינדור רקורסיבי (pre-order: קודם המתכון עצמו, אחר כך הילדים שלו) עבור כל מנה בתפריט, עם **Set גלובלי של "כבר פורט"** (rendered):
   - אם ה-recipeId כבר פורט במקום אחר → מציגים רק שורת הפניה קצרה ("↳ שם — פורט למעלה, כמות X") בלי לשכפל את השלבים.
   - אחרת → מציגים בלוק מלא: שם + כמות כוללת + שלבי הכנה (checkboxes) + ציוד הכנה, ואז ממשיכים רקורסיבית לילדים (רכיבי-מתכון) שלו, בעומק +1 (indentation גדל).
3. לכל בלוק הכנה יש גם checkbox ברמת הבלוק כולו ("ההכנה הזו גמורה") בנוסף לצ'קבוקסים של כל שלב בנפרד.

### 4.4 ציוד לאירוע (equipment aggregation)
מעבר רקורסיבי דומה לסעיף 4.2, אבל עם **הבדל קריטי**: כדי למנוע ספירה כפולה של ציוד כשאותה הכנה משמשת בכמה מנות (למשל דוקסל בשתי מנות שונות צריך את הסירים שלה פעם אחת בלבד, לא פעמיים), משתמשים ב-Set של "מתכונים שכבר ביקרנו בהם באגרגציה הזו" (לא cycle-guard לפי נתיב, אלא deduplication גלובלי לכל האירוע):
```
if (visitedRecipes.has(recipeId)) return;  // הציוד שלו כבר נספר
visitedRecipes.add(recipeId);
for each item in recipe.eventEquipment:
    totals[item.equipId] += item.qty
// המשך רקורסיבית לילדים (kind:'recipe')
```
**שימו לב:** רק `eventEquipment` נספר כאן (ציוד לקחת). `prepEquipment` (ציוד הכנה ביתי) מוצג רק כהערה ליד כל בלוק בעץ ההכנות (סעיף 4.3), ולא מצטבר לרשימת "לקחת".

### 4.5 חישוב עלות (recipe cost)
```
function recipeCostAtFactor(recipeId, factor):
    totals = aggregateIngredients(recipeId, factor)   // כמו 4.2, אבל רק למתכון בודד ולא לכל האירוע
    cost = 0
    for each (ingredientId, netAmount) in totals:
        ingredient = lookup(ingredientId)
        purchaseAmt = purchaseAmountForIngredient(ingredient, netAmount)   // סעיף 3.1
        cost += purchaseAmt * ingredient.price
    return cost

recipeBaseCost(recipeId) = recipeCostAtFactor(recipeId, factor=1)
recipeCostPerBaseUnit(recipeId) = recipeBaseCost(recipeId) / recipe.baseAmount
```
לכל מנה בתפריט אירוע: `factor = servings/baseAmount`, `costForThisOrder = recipeCostAtFactor(recipeId, factor)`.
**עלות אירוע כוללת** = סכום `costForThisOrder` על פני כל המנות בתפריט. **עלות ממוצעת לסועד** = עלות כוללת / `event.guests`.
זו עלות **חומרי גלם בלבד** — לא כולל עבודה/ציוד/הובלה/רווח, ויש לציין זאת במפורש בממשק.

### 4.6 פריטים להביא לאירוע (bring items) — רק לאירועי חוץ (offsite)
לכל מנה בתפריט, עוברים על **הרכיבים הישירים בלבד** (עומק 1, לא רקורסיבי לכל העץ):
- רכיב מסוג `recipe` (הכנה) → פריט "מוכן" שצריך לקחת בקופסה, עם הכמות שחושבה עבורו.
- רכיב מסוג `ingredient` → מרכיב גלם שנלקח כמו שהוא (לדוגמה גבינה לגירוד על מקום).
מצטברים (מסוכמים) לפי id אם אותו רכיב/הכנה מופיע בכמה מנות. **הרעיון:** כל דבר שמקונן עמוק יותר בתוך הכנה כבר "נבלע" בתוך ההכנה המוגמרת שנלקחת כמכלול, ולכן לא רלוונטי ברמה הזו.

## 5. מסכים ופיצ'רים

### 5.1 טאבים ראשיים
מרכיבים | ספקים | ציוד | סועדים | מתכונים | אירועים

### 5.2 מסך מרכיבים
טבלה עם כל השדות מסעיף 3.1. כפתורי מיון **ידניים בלבד** (לא אוטומטי) — "מיין לפי שם" ו"מיין לפי ספק", עם toggle כיוון עולה/יורד בלחיצה חוזרת. בלי לחיצה על כפתור מיון — הרשימה בסדר ההוספה. מרכיב חדש נוצר גם inline מתוך עורך מתכון (הקלדת שם חדש שלא קיים בספרייה יוצרת מרכיב אוטומטית).

### 5.3 מסכי ספקים / ציוד / סועדים
טבלאות CRUD פשוטות. כל אחד עם כפתור מיון ידני לפי שם (toggle asc/desc). מחיקה עם אזהרה אם הרשומה בשימוש במקום אחר (למשל ספק שמשויך למרכיבים, ציוד שמשויך למתכונים, סועד ששובץ באירוע) — במקרה כזה השיוכים מתעדכנים ל-null/מוסרים בהתאם.

### 5.4 מסך מתכונים
רשימת כרטיסים, עם צ'יפים לסינון "הכל / מנות סופיות / הכנות". כל כרטיס מציג: סוג (badge), שם, כמות בסיס+יחידה, מס' רכיבים, מס' שלבי הכנה, **ועלות מחושבת** (סה"כ + ליחידה).

**עורך מתכון:** בחירת סוג (dish/prep), שם, כמות+יחידת בסיס, רשימת רכיבים (עם שתי פעולות הוספה נפרדות: "+ מרכיב גלם" ו-"+ מתכון כרכיב" — השני מסנן מתכונים שהיו יוצרים מעגליות), שלבי הכנה (רשימה דינמית), שני selectors לציוד (הכנה/אירוע) עם אפשרות "+ ציוד חדש" inline, וכל פריט ציוד נבחר מקבל שדה כמות (qty).

### 5.5 מסך אירועים
רשימת כרטיסים (badge לפי סוג onsite/offsite).

**עורך אירוע:** שם, סוג אירוע (radio), תאריך, כמות סועדים, מיקום/הערה (התווית משתנה לפי הסוג), הערות חופשיות (textarea), בניית תפריט (dropdown של מתכוני-dish בלבד + כמות מנות שהוזמנה, ברירת מחדל = כמות הסועדים), ו**רשימת סועדים דינמית**: שורה לכל "מושב" (לפי כמות הסועדים), כל שורה עם dropdown לבחירת סועד קיים (או "+ סועד חדש" עם name/phone/restrictions inline) — לגמרי אופציונלי, אפשר להשאיר ריק.

### 5.6 מסך סיכום אירוע ("הפתק")
מציג לפי סדר:
1. כותרת: שם, תאריך, סוג, מיקום, סועדים.
2. **הערות לאירוע** (אם הוזנו).
3. **פירוט סועדים** (אם שובצו) — כל שורה: שם (ימין) | טלפון (אמצע) | הגבלות תזונה (שמאל, מודגש/צבוע).
4. **רשימת קניות**, מקובצת לפי ספק, עם checkbox לכל שורה.
5. **רשימת הכנות** — עץ מקונן (סעיף 4.3), עם checkbox לכל בלוק הכנה שלם וגם לכל שלב בנפרד.
6. (רק אם offsite) **ציוד לקחת לאירוע** — מצטבר עם כמויות (סעיף 4.4).
7. (רק אם offsite) **פריטים והכנות לקחת** — סעיף 4.6.
8. **עלות חומרי גלם** — פירוט לכל מנה + סה"כ + ממוצע לסועד (סעיף 4.5), עם ההסתייגות שזה חומרי גלם בלבד.

כפתורים: **העתק כטקסט** (לשליחה בוואטסאפ — פורמט טקסט פשוט עם `===` בין סעיפים), **הדפסה** (CSS מותאם להדפסה), **עריכת אירוע**.

מצב הצ'קבוקסים (מסומן/לא) הוא **session-only** בגרסה הנוכחית (לא נשמר) — **בגרסת האתר, כדאי לשקול לשמור את זה ב-DB** (שדה `completed_prep_items` על האירוע, JSON או טבלת קישור), כדי שהצוות יראה התקדמות מסונכרנת בזמן אמת בין מכשירים — זה בדיוק אחד הדברים שהמעבר לאתר אמור לשפר.

## 6. הערות מיגרציה מהארטיפקט הקיים

- הנתונים הקיימים שמורים כ-JSON תחת מפתחות: `ingredients`, `recipes`, `events`, `suppliers`, `equipment`, `guests` (ראו פונקציית `gatherBackupData()` בקוד המצורף — זה בדיוק מייצא אובייקט אחד עם כל שש הרשימות).
- באפליקציה הנוכחית יש כפתור **"ייצוא גיבוי"** שמפיק JSON מלא של כל הנתונים. **מומלץ: לפני תחילת הפיתוח, לייצא את הנתונים הקיימים דרך הכפתור הזה, ולתת את קובץ ה-JSON ל-Claude Code כ-seed data** לאכלוס מסד הנתונים החדש — כך לא צריך להזין הכל מחדש ידנית.
- שימו לב שה-IDs הקיימים הם מחרוזות (לרוב UUID רנדומליים שנוצרו ב-client, כלומר לא בהכרח UUID תקני v4) — כדאי לתת ל-Claude Code להחליט אם לשמר אותם as-is או ליצור IDs חדשים ולמפות בין הישן לחדש בזמן ה-import.

## 7. הצעת סטאק טכנולוגי (לא חובה, המלצה בלבד)

- **Frontend:** Next.js / React, מתארח ב-Vercel.
- **Backend + DB + Auth + Realtime:** Supabase (Postgres). טבלאות מוצעות: `ingredients`, `suppliers`, `equipment`, `guests`, `recipes`, `recipe_components` (טבלת קישור many-to-many עם `kind`, `amount`), `events`, `event_menu`, `event_guest_seats`, `event_completed_items` (למעקב צ'קבוקסים בזמן אמת).
- **PWA:** manifest.json + service worker בסיסי כדי לאפשר "הוספה למסך הבית" בטלפון.
- **Auth roles:** טבלת `profiles` עם עמודת `role` ('admin'/'staff'), ואכיפת הרשאות דרך Row Level Security (RLS) של Supabase.
